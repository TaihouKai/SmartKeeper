# 计划：给 KP 的上下文瘦身、吃上缓存（2026-11-28 起草，2026-11-28 做完，见设计文档第 30 节）

## 起因

线上一局（gpt-6-luna）实测：每轮输入约 15.2 万 token、输出约 3000，约 $0.017。单价低才便宜；
换成 $2/百万的模型，同样的上下文一轮就要 $0.25 以上。世界并不复杂，token 多是因为整块往里倒。

拆开一次裁定调用（6.3 万 token，约 12.2 万字）：

| 部分 | 大小 | 问题 |
| --- | --- | --- |
| 各实体此刻生效的固定条目 | 4.5 万字 | 每个条目连引擎执行用的 `config`、`script` 一起给，还有空字段和缩进；只留 KP 用得上的、压紧以后实测 9600 字 |
| 规则书（含模板字段说明 1.6 万字） | 约 4.4 万字 | 每轮不变，但排在会变的内容后面，吃不到缓存 |
| 世界状态 | 1.9 万字 | 缩进格式；压紧后 1.36 万字。角色卡里玩家写的条目同样带着代码 |
| 其余（推导值、事件、行动、情报……） | 约 1 万字 | 本来就小 |

另外：检定规划（plan）和裁定（adjudicate）同一轮里前后脚各发一遍几乎相同的正文；两者的 system 不同又排在最前面，
互相吃不到缓存。线上记录里命中缓存的部分实测只有开头 500 来字。

## 目标与不做的事

- 目标：每轮实际花费降到现在的一半以下，对所有模型都有效（OpenAI、DeepSeek 都按“开头相同的部分”缓存）。
- 不改 KP 能做的决定，不拿走它裁定要用的信息；只去掉引擎自己执行、KP 用不上的东西，和排版上的浪费。
- 不在这里做资料库（lorebook），也不换模型；那是另外的事。

## 步骤

### 1. 先能量出来

- `llm_call` 加一列缓存命中的输入 token（OpenAI 的 `usage.input_tokens_details.cached_tokens`、
  Anthropic 的 `cache_read_input_tokens`、DeepSeek 的 `prompt_cache_hit_tokens`），迁移 0013；管理台的 LLM 调用面板显示出来。
- 每次调用按模型价格表算出美元（价格表放在配置里：输入、缓存命中、输出各一个价；DeepSeek 的峰谷价也算进去），
  管理台按用途（plan、adjudicate、feedback……）汇总每轮的调用次数、输入、命中、输出和花费，一眼看出钱花在哪一步。
- 一个离线脚本 `scripts/context_size.py`：拿数据库副本，对一局重建 plan / adjudicate / opening 的上下文，
  按段落打印字数，改前改后对比。不调模型、不花钱。

### 2. 固定条目和角色卡上的条目只给 KP 看得懂的部分

- 给 KP 的条目视图：名字、说明、等级等列、参数（可选值和说明）、宝具用法的名字和说明、开关状态、冷却；
  去掉 `config`、`script`、`bonus`、`id` 和空字段。由一个函数统一做（engine 给 KP 的读取接口里），
  世界状态里角色卡上玩家写的条目、`active_presets_all` 都走它。
- 例外：只写了说明的“任意规则”条目，说明本身就是规则，照给。审核角色卡（review）要读代码找 bug，照旧给全部。
- 射程、要不要看得见、冷却这些由引擎检查、不合格的会被拒，KP 不需要自己算；要是试玩发现 KP 确实需要某一项
  （例如射程），只把那一项以一行文字给出，不把代码放回来。

### 3. JSON 压紧

- `kp/render.dumps` 去掉缩进（`separators=(",", ":")`）。世界状态、推导值、情报这些都受益。
- 先在离线脚本上看字数，再用一次无记忆子代理当 KP 跑一轮，确认压紧的 JSON 没让它读错。

### 4. 排序：不变的在前，会变的在后

把每次调用拼成同一个顺序：

1. 共用的 KP 总则（现在 `_common.md`，各用途一样）；
2. 规则书；
3. 剧本（KP 版）；
4. 各实体的固定条目（只在换装备、改卡时变）；
5. 世界状态和本轮的东西（事件、行动、检定结果……）；
6. **最后**才是这次调用自己的任务说明和输出格式（plan、adjudicate、opening……各自的 prompt）。

这样：
- 同一局里所有调用共享 1～4（约 2.5 万 token），一轮内 plan 和 adjudicate 共享到 5 的大部分；
  adjudicate 只比 plan 多出检定结果和任务说明，几乎整份都是缓存价。
- system 里只留 1（各用途相同），任务说明挪进 user 消息末尾。要确认三家接口的缓存都认这种写法
  （OpenAI 的 `instructions` 算前缀；Anthropic 需要在 4 之后打 `cache_control` 断点）。

### 5. 缓存的有效期

- 异步跑团两轮之间可能隔几个小时，默认几分钟的缓存会过期；一轮之内 plan→adjudicate→feedback 是连着的，
  主要收益在这里。
- 每局一个 `prompt_cache_key`（OpenAI），让同一局的调用落在同一份缓存上；查清楚当前模型支不支持更长的保留期
  （有的话按局开），DeepSeek 的磁盘缓存本来就能留很久。

### 6. 验证

- 离线脚本：同一局改前改后每段字数、每轮总 token 的估算。
- 全部检查、端到端测试。
- 无记忆子代理当 KP，用新上下文跑一轮 plan + adjudicate（不调 API），看裁定有没有因为少了代码而出错。
- 上线后看一两轮真实调用的缓存命中列，和估算对一下。

## 预计效果（每次裁定类调用）

| | 现在 | 瘦身后 |
| --- | --- | --- |
| 固定条目 | 4.5 万字 | 约 1 万字 |
| 世界状态 | 1.9 万字 | 约 1.2 万字（压紧 + 去掉条目代码） |
| 总计 | 约 6.3 万 token | 约 4 万 token |
| 按缓存价算的等效 token | 约 6.3 万 | 约 1.5～2 万（共享前缀约 2.5 万按一成算） |

每轮（plan + adjudicate + 几次小调用）等效从约 15 万降到 5～6 万。

## 风险

- KP 读不到代码以后，对“任意规则”以外的条目效果只能靠说明；说明写得差的条目会被理解偏。
  规则书里的说明是我们写的，可以补；玩家写的说明由审核把关（审核照旧看代码，能指出说明和代码对不上）。
- 改顺序会让各用途的 prompt 结构都动一遍，测试里按段落查 prompt 的断言要跟着改。

## 参考：CanonEngine 那边的经验（2026-11-28 问过它的 Claude）

- 它按“不变 → 变化 → 本次主体”排序，实测只省约 4%，因为每轮检索到的历史一半会换；我们的大头是静态的规则书和技能说明，
  只要 plan 和 adjudicate 开头那段**逐字一致**（同样的文本、顺序、序列化），收益会大得多。
- 它也认为紧凑 JSON、不给模型执行代码是纯浪费，不算削减内容。用户在那边的原则：去掉浪费可以，不能让模型看到的世界变少。这里同样遵守。
- 它的上下文分“必需”和“可选”：必需的超预算时报错让人调预算，不悄悄丢；可选的按优先级填预算。我们的记事展开已经有预算，
  以后加资料库（见 plan-lorebook.md）照这个分法。
- 它对模型输出的修复更细：坏的列表项删掉、可选字段的坏值置空、枚举修正，“检查类”列表不修。我们现在是整体重试加少量修复，
  以后便宜模型出错多时可以照这个加。
- 它用“prompt 哈希 + 输入哈希”缓存模型答案、跨局复用（prompt 一改就作废）。我们的角色卡审核已经按校验和复用，同一个思路。
