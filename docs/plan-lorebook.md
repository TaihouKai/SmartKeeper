# 计划：规则包里的资料库（lorebook），按关键词触发（2026-11-28 起草，未开始）

## 起因

KP 需要设定知识（认英灵、宝具效果、魔术协会和教会的规矩），但 API 模型很少主动上网搜：线上一局里只在审核角色卡时搜了 4 次，
限定 tmdict 的搜索一次也没搜到结果。用户手上有现成的 Fate 资料（SillyTavern 世界书格式）。
不希望像 SillyTavern 那样常驻大段设定、每轮多花几美分。

参考：CanonEngine（同一位用户的项目，`C:\Users\agent\claude\SillyTavern-CanonEngine`）的 `src/core/runtime/lore.ts`
（`keyMatch`、`entryMatches`）和 `worldset.ts`（常见词不单独触发）。那边的 Claude 建议只借鉴思路、移植成 Python，不跨语言调用。

## 设计

- **格式**：直接用 SillyTavern World Info 的 JSON（条目的 `key`、`keysecondary`、`selectiveLogic`、`constant`、`disable`、
  `caseSensitive`、`matchWholeWords`、`order`、`content`、`comment`）。用户的世界书原样导入，不另造格式。
- **放在哪**：规则包的一部分（`world.lore`，可以有几本），跟着规则包版本走；管理台规则编辑器里能导入、看、开关条目。
  剧本也可以带自己的几条（剧本专属的设定）。专有名词只出现在规则包和剧本数据里。
- **触发由代码决定**，不让 KP 挑：
  - 扫描的文本：本轮玩家写的行动和聊天、在场实体角色卡上的出处、武器、外观、KP 最近几轮的裁定原文、剧本的 KP 部分；
  - 匹配规则照 World Info：主关键词任一命中，再按次关键词逻辑（any / not_all / not_any / all）；`/正则/`；拉丁文字可选整词；大小写开关；
  - CanonEngine 踩过的坑：出现在很多条目里的常见词（例如“魔术”“英灵”）命中不算；人名单独出现容易误触发，
    可以按条目配置要求和另一个关键词同时出现；
  - 一跳关联：命中条目的正文里提到的别的条目的关键词，再带上（各自计预算）。
- **预算**：每次调用一个字数上限（默认约 6000 字），按命中程度和 `order` 排序填，单条过长截断；
  常驻（`constant`）条目单独计、单独设上限，默认不鼓励。
- **只给需要设定的调用**：检定规划、裁定、开场、审核角色卡、和 KP 聊天。写反馈、泄密检查、起代号不给。
- **在上下文里的位置**：放在会变的内容之前、固定条目之后（命中的条目每轮可能变，放太前会打断缓存前缀）。
- **记录**：每次调用记下触发了哪些条目、为什么（哪个关键词、在哪段文字里），管理台能看到，方便调关键词。

## 步骤

1. 看用户的世界书：条目数、总字数、关键词写法、有多少常驻、常见词有多少；用这一局的真实上下文离线模拟触发，估算每次调用会带进多少字。
2. 数据结构（contracts）和导入（rules：校验、导入 World Info JSON）；迁移规则包数据。
3. 触发（kp 或 engine 的纯函数，带测试：主次关键词逻辑、正则、整词、常见词、一跳、预算截断）。
4. 接进各用途的上下文，记录触发结果。
5. 管理台：导入、条目列表、开关；LLM 调用面板里显示这次带了哪些条目。
6. 验证：离线模拟几轮看触发是否合理；无记忆子代理当 KP 跑一轮看有没有用上；全部检查。

## 成本估算

每次 6000 字约 3000 token。全 Luna：每轮多不到 0.1 美分；裁定用 $2/百万的模型：每轮多约 1.2 美分。
